# Wave 3.5 — Multi-Account Identity Model (Design)

**Date:** 2026-07-05
**Status:** Approved design, pre-implementation
**Depends on:** Wave 3 heartbeat (merged `5b6a531`)

## Problem

Aegis models each login username as a fully separate user (`data/users/<name>/`).
The user is ONE person (Switch) who will link MANY external accounts — some
presenting as "Dustin" (professional), some as "Switch". Today:

- All real data lives under login `dustin` (display_name already "Switch"):
  `google_tokens.json`, `tasks.json`, `events.json`, `contacts.json`, `moods.json`,
  vault PIN, pike/LCARS preferences. Telegram chat ID maps to `dustin`.
- The `switch` login is an empty shell (never used).
- The Wave 3 heartbeat hardcodes `user_id="switch"` (`core/heartbeat/runtime.py:88`),
  so it is **effectively dormant**: recurring_fire sees no tasks, morning_briefing
  has no events/creds and its toggle reads the wrong `features.json`, Telegram
  delivery gets no chat_id, and in-app notifications land in a session the user
  never opens. Failure mode is silence, not leakage.
- Only ONE Google account can be linked per user (`google_tokens.json` is a
  single fixed file), but more accounts are coming: TheSwitchStitch@gmail.com
  (sewing business, soonest), an HBO work account (film production; provider
  possibly Microsoft), later Reel Ballistics and Husky Blue.

## Decisions (from brainstorm 2026-07-05)

1. **Canonical user stays `dustin`** (lowest risk, no data migration). A
   supported **username-rename tool** makes `dustin` → `switch` possible later.
2. **Account layer is provider-shaped, Google-first.** `provider` is a string
   field; only `"google"` is implemented this wave. Non-Google providers slot in
   behind the same record shape later.
3. **Represent-as = name + sign-off + tone hint** per account, injected into the
   compose prompt when drafting from that account. No per-account personas.
4. **Account selection = infer + confirm.** Aegis infers from explicit hints,
   then context (recipient/topic), falls back to the default account; the
   existing draft/event confirmation states the chosen account; "use X instead"
   re-resolves.
5. **Heartbeat jobs aggregate across all linked accounts, labeled** by account,
   with per-account feature toggles.
6. **Scope = identity layer + heartbeat repairs + real Gmail unread wiring for
   inbox_scan.** NOT in scope: linking account #2 (multi-account OAuth settings
   UI), non-Google provider implementations, Wave 4.

## Architecture (Approach A — accounts registry with a provider seam)

### Data model

```
data/users/<user>/
  accounts.json                      # registry — metadata only, NO secrets
  accounts/<account_id>/tokens.json  # per-account credentials
```

`accounts.json`:

```json
{
  "accounts": [
    {
      "id": "google-personal",
      "provider": "google",
      "email": "dustin.jr.lange@gmail.com",
      "label": "Personal",
      "is_default": true,
      "represent_as": {
        "name": "Dustin",
        "signoff": "Dustin",
        "tone_hint": "personal, casual-professional"
      },
      "features": { "briefing_calendar": true, "inbox_scan": true },
      "status": "ok"
    }
  ]
}
```

- `id` is a stable slug, never the email.
- `features` gives per-account opt-out of briefing/scan without unlinking.
- `status` is `"ok"` or `"error"` (set when token refresh fails) so UI/briefing
  can say "X needs reconnecting" instead of silently dropping it.

### AccountManager (`core/accounts/manager.py`)

Constructed by `UserSession.__init__` like the other managers
(`self.accounts = AccountManager(user_data_dir)`):

- `list(feature=None)` — all accounts, optionally filtered by enabled feature
- `get(account_id)` / `default()` — record lookup
- `creds_for(account_id)` — load + refresh that account's tokens (reuses the
  existing refresh logic from `google_tools.py`, path becomes account-aware)
- `resolve(hint)` — fuzzy match on id, label, email substring, represent-as name

### Lazy migration (first touch)

When `AccountManager` loads and finds no `accounts.json` but an old
`users/<user>/google_tokens.json`: create the registry with one
`google-personal` default account, **copy** tokens to
`accounts/google-personal/tokens.json`, verify the copy parses, then rename the
original to `google_tokens.json.migrated` (kept as backup). Idempotent; users
with no tokens get an empty registry. Failure leaves the old file untouched.

### Backward-compat seam

`GoogleProtocol._get_creds()` becomes a thin wrapper for
`session.accounts.creds_for(default)` so existing call sites (briefing, session
calendar, email_ops) work unchanged on day one.

## Consumer flows

### Outbound email & calendar (infer + confirm)

1. Explicit hint in the message ("from SwitchStitch") → `resolve(hint)`.
2. Else infer via the existing email/event classifier LLM call: it gains a
   structured `ACCOUNT=` output field, choosing from the account list (id +
   label + email) included in its prompt. Unrecognized or absent value →
   `default()`. No new LLM round-trip.
3. Confirmation states the account:
   `Draft from Personal (dustin.jr.lange@gmail.com), signed "Dustin": …`
   "Use X instead" re-resolves and re-drafts.

Represent-as block (name, signoff, tone_hint) is injected into the compose
prompt for the chosen account. LLM inference stays local per existing
sensitivity rules; represent-as is metadata, not new egress.

### Briefing (aggregate, labeled)

`generate_narrative_briefing` loops `accounts.list(feature="briefing_calendar")`,
tags events `[Label] …`. A failing account logs, is marked `status="error"`,
and is skipped — the briefing still renders.

### Heartbeat repairs

- `build_runtime()` loses the `"switch"` default; `server/app.py` passes
  `CONFIG["heartbeat"]["primary_user"]` (set to `"dustin"`). Missing/unknown
  value → loud startup warning, not a silent empty user.
- This alone fixes: recurring_fire (real tasks.json), briefing toggle (reads the
  features.json the UI writes), Telegram delivery (chat ID maps to `dustin`),
  notification target (the session the user actually opens).
- **inbox_scan goes live:** wire the Task-13 seam (`session.fetch_unread_emails`)
  to a real implementation looping `accounts.list(feature="inbox_scan")`,
  calling `gmail_list_messages(q="is:unread")` per account, returning
  `[{"from", "subject", "account"}]`. Ranking logic untouched; notification
  lines gain the account tag. No eligible accounts → `None` → job self-disables
  as designed.
- Document `important_senders` / `keywords` / `notify_threshold` defaults in
  `core_config.json`.

## Username-rename tool (`tools/rename_user.py <old> <new>`)

Run with the server stopped.

1. **Preflight:** new name valid/lowercase/not taken; old exists; server not
   running.
2. **Backup:** zip `data/users/<old>/` + `users.json` + `telegram.json` to
   `data/backups/rename-<timestamp>.zip`.
3. **Rename in order:** `users.json` key → `data/users/<old>/` dir →
   `telegram.json` user_mappings values → `heartbeat.primary_user` config.
   These four locations are the COMPLETE registry of username storage; any
   future feature storing a username must be added here.
4. **Dry-run by default**; `--apply` executes. Restart picks up the new name.

**Guard test:** repo-wide test asserts every known username-keyed storage
location is covered by the rename tool's list, so future hardcodes are caught
at PR time.

### Cleanup

Delete `users.json` entries + dirs for `switch`, `plan_test_user`, `uicheck`,
`testbot` (backup-first).

## Error handling

- Token migration: verify-before-rename; failure leaves original untouched.
- `creds_for()`: refresh on expiry; on failure return `None`, mark account
  `status="error"`.
- Per-account fetch failures in briefing/inbox_scan never kill the aggregate.

## Testing

- **AccountManager:** registry CRUD, `resolve()` hints, default selection, lazy
  migration (backup exists, idempotent, empty-registry case).
- **Consumers:** briefing aggregates two fake accounts with labels; erroring
  account degrades gracefully; email_ops confirmation includes account +
  represent-as; inbox_scan multi-account unread with tags.
- **Heartbeat:** `build_runtime` honors `primary_user`; warns on missing config.
- **Rename tool:** full rename on temp data dir; dry-run is read-only; guard
  test for location completeness.
- **Holistic whole-feature review at the end** (standing rule from Waves 2/3):
  hunt cross-cutting leaks — e.g. does any represent-as or account metadata ride
  into a cloud payload it shouldn't?

## Out of scope

- Linking TheSwitchStitch@gmail.com / multi-account OAuth settings UI (next wave)
- Non-Google provider implementations (HBO account may be Microsoft — provider
  field accommodates it, implementation deferred)
- Wave 4 (Tailscale HTTPS + voice loop)
